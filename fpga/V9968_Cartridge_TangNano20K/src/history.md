### Dragon Quest II（MSX2）タイトル画面のロゴ欠け

- 現象: ロゴのスクロールが止まり盾と重なると、ロゴ中央（スプライト）が消える。
- 調査: ROM の逆アセンブルとダンプ用 ROM で解析した。YMMM 転送とキャッシュは正常だった。ゲームの VSYNC 割り込み処理が S#0 の 5S を検出すると、0x7600〜0x767F（停止後のスプライトアトリビュート）を毎フレーム `E0 00 00 00` で上書きしていた。

## 2026-11-07 スプライト CC=1 の Sprite#0 が表示される問題の修正

### 現象

- AshGuine Story III（Microcabin）のデモで、ゴミのようなスプライトが表示された。CC=1 の Sprite#0 が表示されていた。

### 原因

- `vdp_sprite_makeup_pixel.v` では、plane N を phase N で選択し、その情報が `ff_color_*` に届くのは phase N+4 である。
- ところが、合成の初期化（最初のプレーンの処理）と、合成結果のラッチを phase 3 で行っていた。
- そのため phase 3 で、前のスロットの plane15、または使っていないプレーン枠に残っている CC=0 のデータを拾っていた。合成部はこれを「CC=0 のプレーンが先にあった」と誤判定するので、続く Sprite#0 が CC=1 でも表示されていた。
- 同じ原因で、16枚表示時の plane15 が1画素右にずれていた。

### 修正内容

- 合成の初期化と結果のラッチを phase 4 に変更した。
- 衝突判定で除外する phase を 1 から 4 に変更した。phase 4 では合成状態がまだ前の画素の結果のため、判定から外す。これにより、plane13 が関わる衝突も検出するようになった。
- 表示の水平位置（パイプライン遅延）は変わらない。

### 確認

- 単体ベンチ9ケースを修正前と修正後の RTL で実行した。対象は CC=1 単独、CC の OR 合成、優先順位、衝突、plane7/plane15、16枚中 plane0 が CC=1 の場合など。修正前は4ケースが FAIL、修正後は全ケース PASS。
- 既存の `test_vdp_timing_control` も PASS した。
- 実機でデモのゴミが表示されなくなったことを確認した。

### SCREEN10/11 (YJK+YAE) で A=1 のパレット画素が黒くなる問題

- 原因は `vdp_color_palette.v` の3点。

### Geo3D の clk85m → clk42m ホールド違反対策

- clk42m の立ち上がりは clk85m の立ち上がりと一致するため、立ち上がり同士の受け渡しはホールド関係が 0ns となり、SDC のホールド不確かさ 0.5ns より短い配線（`a_data → texy` 0.480ns など）で違反していた。データが速く着きすぎることが原因のため、FF 複製による負荷分散は逆効果と判断した。
- `geo3d_bus.v` で、`req_t`/`a_sel`/`a_wr`/`a_data` を clk85m の立ち下がりで取り直すコピー FF（`syn_preserve` 指定）を追加した。エンジン側では req 検出時に `e_wr`/`e_rd` と同時に `e_sel`/`e_din` へ取り込み、エンジンへ渡す。受け渡しは立ち下がり→立ち上がりの FF 1段となり、ホールドに半周期の余裕ができる。req 検出の clk42m エッジ、ack、busy の動作サイクルは変わらない。
- 立ち下がりのコピーをエンジンへ直結する案は、エンジン内部の深いロジックのためセットアップが -5.2ns となり不採用。SDC の `set_false_path` による除外も修正ではないため採用していない（SDC は変更なし）。
- `test_hmmv` の2本は PASS。別ディレクトリでの全体合成・配置配線で setup/hold 違反0件、最小 slack は setup +0.103ns、hold +0.074ns。新しい受け渡しのセットアップは +3.934ns。Register 8975 → 8995。
- 途中の配置では Geo3D 外の `ff_vs → hdmi_converter`（clk85m → clk42m）が -0.035ns になったことがある。再発した場合は同様の方法で対策できる。実機では未検証。

## 2026-11-01 VRAM 読み出しの先読みと WAIT

- 99h/89h で読み出しアドレスを設定した時点と、98h/88h から読み出した後に、次の VRAM データを先読みする。98h/88h への書き込み値も読み出しバッファに反映し、アドレスは次のアクセス先を指す。

- ポートオフセット6は MegaRAM 用に予約されているため、VDP からの応答を停止してバスを解放する。
- `test_vram_prefetch_wait` を追加し、リフレッシュによる遅延、連続読み書き、キャッシュ退避、他ポートとの分離、14/17/18bit のアドレスラップ、読み出し待機中のリセットを確認した。先読み済み読み出しの応答は RTL シミュレーション上で最大約110ns。System Controller のポート分離、共有キャッシュ、VDP のレジスタ・ステータス関連テストも通過した。
- Gowin の検証では、従来の `Map_Option=3` で setup 違反58件、hold 違反6件だったため、プロジェクト設定を `Map_Option=1` に変更した。プロジェクト設定を用いた別ディレクトリでの再合成・配置配線は setup/hold 違反ともに0件、Logic 16545/20736、LUT 13941、ALU 2484。最小 slack は setup +0.092ns、hold +0.047ns と余裕が小さい。
- 実機では未検証。MSX スロットの外部遅延制約はなく、R800 の WAIT サンプリングを含む基板上のタイミングは別途実機で確認する必要がある。

## 2026-09-29 Fleet Commander II 起動停止の調査・ポート#1ラッチ修正

### 症状

- 実機MSX（内蔵VDP無効化）にV9968カートリッジを装着し、別スロットのASCII8Kメガロム「Fleet Commander II」を起動すると、212ライン化→画面一面シアンの後、黒画面になる前に停止した。本物のVDPでは正常起動する。

### 調査

- ROM(ASCII8K)の起動経路を逆アセンブルで追跡。H.STKE経由でバンク0 `405Eh` → `CHGMOD 7`、ページ1への64KB `BIGFIL` → RAM `D011h`（スロット走査・FM音源検出・H.TIMI設定） → バンク28 `4BE0h` → バンク29 `41EBh` → `4745h` で画面初期化。シアンは `6461h` の表示OFF（R#7=7の周辺色）。
- 停止地点の切り分けのため、指定地点で `DI`→R#7に目印色→`JR $` を実行するパッチROMを作成。バンク29 `41EBh`（赤）は到達、バンク2 `62FFh`（緑）は未到達で、停止箇所をバンク2 `6372h` 内に特定。
- `6372h` はポート99hへ `00,22,81,0F,86,00,88` の奇数バイトを書き込み、組がずれる。本物のV9938/V9958はポート98hの読み書きや、いずれかのポートの読み出しで99hの1バイト目の保持を取り消すため、直後の `CLRSPR` の98h書き込みで組が復帰する。V9968は99h書き込みでしか組の状態が変わらず、以降のレジスタ書き込みがずれ続け、CE待ちから抜けられなくなっていた（誤ったR#46書き込みで転送待ちコマンドが起動したと推定）。
- ゲーム内のステータス読み出し（99h read）は、CE待ち（S#2 bit0）、HMMC/LMMCループ（S#2 bit0/bit7）、POINT（S#7）のみ。S#0のF、S#1、S#2のHR/VRでの分岐はなく、ステータス値の差異は原因ではなかった。
- 実機で `SCREEN 7`→表示OFF→R#8=0→`CLRSPR`→`CLS`→`SCREEN 5` を99hへ必ず2バイトずつ書くBASICで再現したが停止しなかった。奇数バイト書き込みが再現条件。

### openMSXの挙動（`VDP.cc` の `writeIO`/`readIO`）

- 98h書き込み、および98h〜9Bhいずれの読み出しでも `registerDataStored`（99hの1バイト目保持）を取り消す。
- 9Ah（パレット1バイト目）と9Bhの書き込みは保持を取り消さないが、共有の `dataLatch` を上書きする。パレット2バイト目のR/Bもこの `dataLatch` から取る。
- パレットのバイトカウンタ（`paletteDataStored`）はR#16書き込みでのみリセットされる。

### RTL変更（`vdp_cpu_interface.v`）

- 98h書き込み、またはいずれかのポートの読み出しで `ff_2nd_access` を0に戻す。
- 通常パレット（V9938形式）の1バイト目を `ff_1st_byte`（99h/9Bhと共有）に格納し、2バイト目でそこからR/Bを取り出すよう変更。
- 拡張パレットモード（R/G/B 3バイト）のカウンタは独立のまま、R#16書き込みで0に戻す挙動も維持。拡張パレットの書き込みは共有ラッチを変更しない。
- 実機でFleet Commander IIの起動を確認（ラッチ取り消し修正時点）。パレットのopenMSX準拠化は合成・実機未確認。

### テスト

- `test_vdp_cpu_interface/tb.sv` に `tb_port1_latch_reset` を追加（test001〜test012）。98h書き込み・98h読み出し・ステータス読み出しでの取り消し、9Ah/9Bh書き込みでの保持と値の置き換え、パレットR/Bの共有ラッチ参照、R#16およびステータス読み出しとパレットカウンタの関係、拡張パレットの独立性を確認。`run.bat` から実行するよう追加。
- ModelSimで全件エラー0。修正前RTLではtest002で失敗することを確認。既存の `tb_sprite_overmap_status` も通過。

### 注意点

- `test_vdp_cpu_interface` の既存 `tb` モジュールはDUTのポート構成が古く、vsimの読み込みで失敗する（今回の変更以前から）。
- 9Ahが共有ラッチを上書きする挙動はopenMSXの実装に準拠したもので、実機での裏付けは未確認。
- R#8のVR=0でCPUアドレスを16KB折り返す実装は、openMSX（CPU・コマンド・表示すべてに16KBマスクとアドレス入れ替え）と異なる。今回のゲームでは実際にはR#8が書き込まれないため影響なし。
