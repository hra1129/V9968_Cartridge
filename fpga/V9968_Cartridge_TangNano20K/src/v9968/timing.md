# V9968 水平タイミング設計（R#26/R#27 実効値ラッチ位置）

MSX2+ 起動ロゴの櫛形スクロール乱れ対策として、R#26/R#27 の実効レジスタへのコピー位置を
「1ライン中の固定位置」に決めるための設計資料。コード変更前のタイミング確認用。

## 1. 座標の定義

| 項目 | 値 | 備考 |
|---|---|---|
| クロック | 85.909MHz | |
| 1ドット | 16clk | `screen_pos_x[3:0]` = sub-phase (0..15) |
| 1ライン | 5472clk = 342ドット | `ff_half_count` 0..5471 |
| X 座標 | −40 .. 301 | `screen_pos_x = half_count − 640`、14bit 符号付き、`[13:4]` がドット |
| ライン切替 | X=−40 | `screen_pos_y` 更新 |
| VRAM スロット | sub-phase 1 (timing_a: BG/Sprite/Command), 9 (timing_b: CPU/Command) | BG/Sprite の要求は sub-phase 0 |
| 表示画素 | グラフィック: 画面画素 P は X=P+5 で BG から出力 | `ff_left_mask_pos`=13 (8+5) と整合 |

以下「固定」は無シフト X、「シフト」は `X − R#27(実効値)` を基準とするイベント。

### 重要な事実

* 8ドット組は R#27 分シフトしているため、**最後の組は X=255 ではなく X=255+k（最大 262）まで続く**。
  この組にはスプライト属性読み出し (phase 2/4) と `selected_en` が含まれる。
* R#27 を参照する最後のイベントは `start_info_collect`（X=259+k、最大 266/14）。
* info_collect 自身は sub-phase だけで動く。開始後に R#27 が変わっても影響しない
  （リセットは次ラインの X=k−1）。

## 3. 案A: X=256 でラッチ（表示処理停止直後）

| 衝突 | 内容 |
|---|---|
| スプライト選択の最終組 | X=248+k..255+k の組の途中で R#27 が変わり、phase がずれる。読み飛ばしや二重読みが起きる |
| スプライト `h_active` 終了 | k が 7 から 0 に減ると、シフト X が 249 から 256 へ飛ぶ。`==255` を通過しないため `h_active` が落ちない |
| `start_info_collect` | シフト X の 259 を飛び越すと info_collect が起動しない。逆向きの変化では2回起動しうる |
| YJK の最終 J/K | `pixel_phase_x` がずれ、SCREEN10〜12 の右端の J/K の組がずれる（画面全体の4画素ずれ自体は V9958 の仕様） |

案Aを成立させるには、上記をすべて固定 X（または ff_phase 由来）へ書き換える必要がある。
特にスプライト選択の最終組は BG と同じ phase に揃える必要があるため、シフト基準を外せない。

## 4. 案B（採用）: X=267 でラッチ（シフト処理がすべて終わった直後）

「R#27 シフト基準のイベントが1ライン分すべて終わった直後」に、R#26 と R#27 を組で実効値へコピーする。

* 比較: `w_screen_pos_x == {10'd266, 4'hF}` → X=267 から有効
* 対象: R#26, R#27 を同時に（値にもライト時刻にも依存しない固定位置）

### 重なりチェック

| チェック項目 | 区間 | ラッチ 267 との関係 | 判定 |
|---|---|---|---|
| シフト基準イベント | −1+k .. 266 | すべて 267 より前 | OK |
| 8ドット組（VRAM 読み） | k .. 262 | 267 より前 | OK |
| BG 画素パイプライン | 5 .. 260 (+palette 遅延 ≈ 5) | R#27 を参照するのは J/K ラッチ（≤262）のみ | OK |
| info_collect | 259+k .. 次ライン −28 | 跨ぐが R#27 非依存 | OK |
| VRAM リフレッシュ | −16 | info_collect 終了（≤−28）後 | OK |
| 走査線割り込み | 264 | 割り込み処理の OUT は早くても 280 以降 | ラッチの後（後述） |
| ロゴの R#26 書き込み | 前ライン 282 .. −14 | 区間外 | OK |
| ロゴの R#27 書き込み | −39 .. +7 | 区間外 | OK |

ロゴのライト区間は「282 → 翌ライン +7」で、ラッチ 267 はその外側にある。
したがって衝突ライン N の書き込みは、N+1 の X=267 で組でラッチされ、N+2 から反映される。
これは実機動画（N+2 反映）と一致する。
また、ラッチ位置をこの位置に置いた実験（X=264 で組ラッチ）では 84/84 OK だった。

### 現行 OCM 方式が失敗する理由（比較）

ラッチ位置（R#27: −16、R#26: −10+k）がロゴのライト区間（282 .. +7）の内側にある。
そのため、ポーリングの揺れ（31T）によってラッチ前に書かれる場合と後に書かれる場合が混在する。
その結果、N+1 反映と N+2 反映が混ざる（シミュレーションでも R#27 が N+1/N+2 に分裂）。

## 5. 走査線割り込み (Space Manbow) への影響

* 割り込みは X=264 に発生する。その後、Z80 の命令完了待ち、IM1 の応答（13T 以上）、ハンドラの OUT を経る。
  このため R#26/R#27 の書き込みは早くても X≈280 以降になる（1T = 24clk = 1.5ドット）。
* 案B（267）では割り込みからの書き込みは常にラッチ後になり、**次々ライン (N+2) から反映**される。
* 現行 OCM 方式（−16）でも、書き込みが 41T 以内に終わらなければ同じく N+2 になる。
  Space Manbow のハンドラは通常これより長いため、挙動は変わらない見込み。
* 実機の Space Manbow で、ラスタスクロールの境界ラインが1ラインずれていないかを確認する。

## 6. R#18（参考、今回は対象外）

* R#18 は vdp_upscan.v の line buffer 書き込み位置にライブで効いている。
  ライン途中で書き換えると、そのラインの周辺色を含めて書き込み位置がずれる。
* ラッチする場合は、書き込みの切れ目（ライン切替 X=−40）が候補。R#26/R#27 とは別問題として扱う。

## 7. リスクと確認事項

| 項目 | 内容 | 確認方法 |
|---|---|---|
| YJK の右端 | J/K の最終ラッチを ≤262 と見積もった（delay0..4 の段数から）。SCREEN10〜12 で画面全体が4画素ずれるのは V9958 の仕様 | SCREEN12 で右端を確認 |
| テキストモード | R#26 は無効で、R#27 による 0〜7 ドットのスクロールのみ。phase 周期は6、開始は 7+k、終了は固定 252。267 より前に完結 | SCREEN0 で横スクロール |

## 8. 検証計画

1. SSG 単体テスト (`test_vdp_timing_control_ssg`): ラッチ位置の期待値を `14'h10AF`（X=266/F）に変更し、R#26/R#27 が同時に更新されることを確認する。
2. ロゴベンチ (`test_top_SCREEN6_LOGO`, `apply_line=2`): frame 0–2, 40–42 で 84/84 OK、MIDLINE なし。
3. 実機: MSX2+ 起動ロゴ、Space Manbow、ZANAC EX（R#23 系の回帰確認）。

## 9. 現状（2026-11-11、ペンディング）

* X=267 の組ラッチを採用した。ロゴベンチ（frame0〜42）では、レジスタ判定も画素照合もすべて一致した。
* 実機（SX-2 + V9968）では大幅に改善したが、前半の高速移動中に2ラインがまとまって動く箇所がまだ残る。
* 疑わしい要因: SX-2 の CPU クロックは 50MHz から PLL で作っており、3.579545MHz ちょうどではない。V9968 の 28.63636MHz の8分周とのずれで、R#26 の余裕（約10T）を越えることがありうる。
* 実害は小さいので、この件はペンディングとする。CPU も 3.579545MHz で動く FPGA MSXtR が届いたら再確認する。改善が必要なら、2段ラッチ（S≈144 で取り込み、267 で実効レジスタにコピー）を候補とする。
